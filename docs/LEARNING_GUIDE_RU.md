# CloudDesk: разобраться перед собеседованием

## Что такое пет-проект

Пет-проект — небольшое приложение для практики и портфолио. Оно показывает, какую задачу решает код, как его запустить и как проверить результат. Не требуется придумывать заказчика или коммерческий опыт.

CloudDesk — **учебный журнал заявок на серверные ресурсы**. Например, студенту нужен сервер для сайта: 2 процессорных ядра, 4 ГБ памяти и 40 ГБ диска. Он создаёт заявку. Оператор одобряет или отклоняет её. На странице видны заявки и сумма согласованных ресурсов.

Этот проект подготовлен с помощью AI. В портфолио можно прямо назвать его учебным проектом с AI-помощью. Твой вклад постепенно становится конкретным: ты запускаешь приложение, разбираешь логику, проверяешь поведение и самостоятельно вносишь изменения.

## Из каких частей состоит приложение

**Frontend** — то, что видно в браузере: форма, карточки и кнопки. Его файлы находятся в `src/main/resources/static/`.

**Backend** — Java-программа, которая проверяет данные, решает, разрешено ли действие, и сохраняет результат. Она запускается на твоём компьютере.

**База данных** — постоянное хранилище заявок. Без неё данные пропали бы после остановки приложения. Здесь H2 сохраняет их в файл `data/clouddesk.mv.db`.

**API** — согласованные адреса и правила общения с backend. Например, «отправь описание заявки на `/api/requests`, получи её ID и статус».

**HTTP** — способ передать запрос и получить ответ. У запроса есть метод, адрес и иногда тело с данными. В ответе приходят код результата и данные.

**JSON** — текстовый формат этих данных: `{"title":"Учебный сервер","cpu":2}`. Это лишь пример формата; для создания заявки нужны и остальные обязательные поля.

| Действие | Запрос | Успешный ответ |
|---|---|---|
| Показать список | `GET /api/requests` | `200`, массив заявок |
| Создать заявку | `POST /api/requests` | `201`, новая заявка |
| Одобрить | `PATCH /api/requests/1/status` с `{"status":"APPROVED"}` | `200`, обновлённая заявка |
| Показать сводку | `GET /api/stats` | `200`, количества и суммы |

Адрес `127.0.0.1` означает «этот компьютер». После запуска страница доступна на `http://127.0.0.1:8080`.

## Путь одной заявки по коду

Открой эти файлы в указанном порядке. Все Java-пути ниже начинаются с `src/main/java/dev/olsa777/clouddesk/`.

1. В браузере пользователь нажимает «Создать». JavaScript отправляет `POST /api/requests`.
2. **`request/RequestController.java`** принимает запрос. Controller — вход в приложение: он связывает HTTP-адрес с Java-методом.
3. **`request/CreateRequest.java`** описывает входные поля. Аннотации вроде `@NotBlank` и `@Min(1)` проверяют обязательность и границы. Если CPU равен нулю, запрос отклоняется до сохранения.
4. **`request/RequestService.java`** выполняет операцию. Service связывает шаги задачи и управляет транзакцией — группой изменений, которая должна успешно завершиться целиком.
5. **`request/ResourceRequest.java`** представляет одну заявку в базе: название, ресурсы, статус, даты. Новая заявка получает статус `NEW`.
6. **`request/RequestRepository.java`** сохраняет и читает заявки. Repository — доступ к базе. Spring Data JPA предоставляет базовые методы вроде `save` и `findById`.
7. **`request/RequestView.java`** собирает поля ответа. Backend возвращает JSON, а браузер обновляет список.

При смене статуса используется **`request/UpdateStatus.java`**, а допустимость перехода определяет **`request/RequestStatus.java`**. Ожидаемые ошибки оформляет **`api/ApiExceptionHandler.java`**.

Controller принимает, Service выполняет задачу, Repository работает с хранилищем. Такое разделение помогает менять одну часть, не переписывая всё приложение.

## Статусы и ошибки

```text
Новая (NEW) → Согласована (APPROVED) → Условно выделена (PROVISIONED)
      └────→ Отклонена (REJECTED)
```

Нельзя выделить ресурсы до согласования, вернуть конечную заявку назад или одобрить её второй раз. Сервер проверяет это даже при обходе кнопок и прямом обращении к API.

- **400 Bad Request:** сам запрос неверный. Например, CPU = −1 или неизвестное окружение.
- **404 Not Found:** заявки с таким ID нет.
- **409 Conflict:** запрос понятен, но не подходит к текущему состоянию. Например, попытка одобрить уже отклонённую заявку.

В сущности также есть `@Version`. Это защита от потери обновления: если два оператора одновременно прочитали одну версию заявки, второй не сможет молча затереть решение первого. Он получит конфликт и должен обновить данные.

В суммы ресурсов входят `APPROVED` и `PROVISIONED`. Переход между ними **не удваивает** сумму: это всё та же заявка. Новые и отклонённые заявки в ресурсные суммы не входят.

## H2, PostgreSQL и настоящее облако

**H2** удобна для первого запуска: она работает внутри приложения и не требует отдельного сервера. В обычном запуске данные находятся в файле; в тестах — в памяти, отдельно от твоих заявок.

**PostgreSQL** — отдельный сервер базы данных. Для него нужны запущенный PostgreSQL, база, пользователь и пароль. В проекте есть профиль `postgres`, но автоматические тесты этого проекта запускались с H2. Наличие профиля ещё не доказывает проверенную работу на PostgreSQL.

В CloudDesk кнопка выделения ресурсов **меняет запись в базе**. Настоящая виртуальная машина не появляется. В реальном облачном сервисе потребовались бы API провайдера, права доступа, обработка длительных операций и ошибок, проверка лимитов и подтверждение результата. Это возможное развитие, а не уже выполненная работа.

## Как проверить проект самому

Из корня проекта:

```bash
./mvnw test
./mvnw spring-boot:run
```

На Windows вместо `./mvnw` используй `mvnw.cmd`. Для первого запуска нужен интернет: Wrapper скачает Maven и зависимости.

**Автоматический тест** — код, который выполняет сценарий и сравнивает результат с ожидаемым. Если поведение случайно сломано, тест сообщает об этом.

- `src/test/java/dev/olsa777/clouddesk/request/RequestStatusTest.java` проверяет все 16 пар исходного и целевого статусов.
- `src/test/java/dev/olsa777/clouddesk/RequestApiTest.java` проверяет запросы через MockMvc, настоящую логику Spring и тестовую H2: создание, фильтры, сводку, ошибки и защиту от устаревшего обновления.
- MockMvc позволяет проверить HTTP-слой без запуска внешнего браузера и сетевого порта. Проверку интерфейса в браузере он не заменяет.

Для ручной демонстрации создай две заявки. Одну одобри и отметь выделенной, вторую отклони. Проверь, что суммы учитывают только первую. Перезапусти приложение: заявки должны остаться. Примеры `curl` для ошибок есть в основном [README](../README.md).

## Рассказ на 60 секунд

> CloudDesk — мой учебный проект для разбора Java backend и связи сервера с интерфейсом. Он помогает оформить заявку на CPU, память и диск, согласовать её и показать сводку ресурсов. Backend написан на Spring Boot, данные сохраняются через Spring Data JPA в H2. Интерфейс обращается к REST API. Основная логика — проверка полей и разрешённых переходов статусов: например, новую заявку нельзя сразу отметить выделенной. Для таких конфликтов сервер возвращает 409. В проекте есть автоматические тесты API, статусов и статистики. Выделение здесь демонстрационное, реального подключения к облаку нет. При подготовке использовались AI-инструменты; я разбираю код и могу показать, как запрос проходит от контроллера до базы.

Используй последнюю фразу о разборе кода, когда действительно пройдёшь этот путь. После упражнения добавь конкретику: «Самостоятельно изменил … и проверил …».

## Семь вопросов на собеседовании

**1. Какую задачу решает проект?**  
Упорядочивает заявки на серверные ресурсы: сохраняет условия, показывает решение и считает согласованный объём. Это учебная модель процесса.

**2. Чем frontend отличается от backend?**  
Frontend показывает форму и результат. Backend проверяет данные, применяет правила и сохраняет изменения. Проверки только в браузере недостаточно: запрос можно отправить напрямую.

**3. Зачем Controller, Service и Repository?**  
Чтобы разделить обязанности. Controller знает HTTP, Service выполняет операцию, Repository читает и сохраняет данные. Правила переходов находятся в модели заявки и её статусах.

**4. Почему запрещённый переход возвращает 409, а не 400?**  
Тело запроса может быть корректным, например `APPROVED`, но заявка уже отклонена. Проблема в конфликте с её текущим состоянием. 400 подходит для некорректных входных данных.

**5. Что произойдёт при одновременном изменении заявки?**  
JPA проверит поле `@Version`. Если сохранённая версия уже изменилась, устаревшее обновление отклоняется. Клиент получает 409 и должен перечитать заявку.

**6. Что проверяют тесты и чего они не гарантируют?**  
Они проверяют бизнес-правила, API и хранение в тестовой H2. Это помогает заметить поломки после изменений. Они не доказывают работу PostgreSQL, всех браузеров или реального облачного API.

**7. Что бы ты добавил следующим?**  
Начал бы с небольшого улучшения, которое смогу закончить и проверить: например, фильтра по окружению. Затем — пагинация, история статусов и права заявителя/оператора. Для настоящего облака понадобятся отдельная интеграция и обработка её ошибок.

## Три самостоятельных упражнения

**1. Измени ограничение CPU с 32 до 16.**  
Найди ограничение в `CreateRequest.java`, обнови максимум и сообщение. Обнови соответствующее поле формы и описание в README. Добавь проверки: `cpu:16` принимается, `cpu:17` получает 400. Запусти тесты. Объясни, почему серверное ограничение обязательно даже при ограничении в форме.

**2. Добавь фильтр списка по окружению.**  
Сделай `GET /api/requests?environment=STAGING`. Продумай совместное применение со статусом. Проверь, что фильтр возвращает только подходящие заявки, а неизвестное окружение даёт 400. Затем добавь выбор окружения в интерфейс.

**3. Добавь счётчик заявок для production.**  
Добавь `productionRequests` в ответ `/api/stats`, считая все заявки с окружением `PRODUCTION` независимо от статуса. Покажи число в интерфейсе. В тесте создай две production-заявки и одну development-заявку: ожидаемое значение — 2.

Начни с первого упражнения. После завершения сделай Git-коммит с конкретным названием, например `Limit requests to 16 vCPU`, и сохрани результат тестов. Это станет небольшим изменением, которое ты действительно понимаешь и можешь защитить на интервью.
